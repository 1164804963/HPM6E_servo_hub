# HPM6E80 CAN适配（原工程对齐口径）

当前目标是适配先楫MCU和HPM6EMotorV20。原生问题的优化按阶段单独进行；参见[原生问题清单](CAN_NATIVE_ISSUES.md)。前期015→415旧优化已撤回，旧报告仅作历史记录；A01重新定义了独立请求/应答ID协议，见下文普通CAN_CIA402章节。

## 硬件与构建

J8使用MCAN4，PC16/PC17为TXD/RXD，PC18控制收发器待机；J9/MCAN7本阶段不初始化。CAN时钟80MHz，支持1Mbps和500kbps。默认节点0x15、1Mbps。

构建：`pwsh -NoProfile -File tools/build_hpm6e80.ps1 -Bus CAN_CIA402`。旧同ID兼容构建加`-LegacySameId`。还可选CANOPEN_CIA402、CAN_ENCOS、CANFD_CUSTOM和ETHERCAT。`-CanPassthrough`打开MAVLink CAN FD通道。可配置不等于协议全部实现：ENCOS仍是原工程的空接收，CUSTOM仍是诊断回显。

## 普通CAN_CIA402协议

默认使用独立请求/应答ID：请求ID就是节点号，范围0..0x3FF；应答ID为`request | 0x400`。默认节点0x15，应答为0x415。只有构建时显式加`-LegacySameId`（CMake `SERVO_CAN_LEGACY_SAME_ID=ON`）才退回原同ID方式，并允许节点0..0x7FF；该开关只影响普通CAN_CIA402，CANopen、ENCOS、CUSTOM和EtherCAT不受影响。

节点上限为1023（0x3FF）。初始化时越界直接拒绝，不进入总线；运行中`set_app_Can_id`在写入数据库和BSP前拒绝，返回`APP_PARAM_OUT_OF_RANGE`。Legacy模式保留标准11位ID范围，也保留原有同ID双向竞争限制。

请求载荷：`[op, index_lo, index_hi, subindex, value_le]`，value为1/2/4字节；op=0读、op=1写。成功应答固定8字节，前4字节保持op/index/subindex，后4字节为回调处理后的值。A02起，OD回调返回错误时回复`[0x80,index_lo,index_hi,sub,abort_code_le32]`，不再回显请求值冒充成功。成功回复表示回调接受，不代表异步动作或实际运动已经完成，仍需观察相应状态。原有子索引和模式检查缺口不在适配阶段优化。

默认节点SLCAN示例（末尾CR）：

```
t01580041600000000000    # 读6041:00，回复t4158...
t0156014060000000        # 写6040:00=0（失能），回复t4158...
t01550160600003          # 写6060:00=3（PV），只说明协议，不作为运动验收
```

应答由128槽软件队列缓冲：RX中断解析请求并同步执行OD回调（控制字不排队、不延迟），只把8字节应答和收包时确定的应答ID入队；前台`servo_can_poll()`每圈最多提交8帧。MCAN TXFIFO满时保留队首、下次重试，不计丢包；其他发送错误丢弃该应答并计入txerr。队列满时先拒绝执行OD回调并同时增加reply drop和txerr，避免形成没有应答的部分动作。队列只保存应答，不保存或重放控制字；128槽是有界容量，不承诺超过128的无限突发不丢。

Legacy同ID模式仍有原生的双向竞争限制，主机应保持单请求在途或足够间隔。不把无节流突发当正常通信。回包仍不代表所有应用动作已执行成功。

HPM6E80的SDK未启用`CAN_SOC_TX_RX_BUFFER_ACCESS_WORKAROUND`；`mcan_transmit_via_txfifo_nonblocking`提交时只检查TXFIFO并写寄存器，没有等待接收活动的忙等。前台发送只使用短临界区保护队列索引和这次非阻塞提交，不关闭长中断。

本阶段的0x400应答分区是显式的新协议变更，不是恢复此前被撤回的015→415旧优化。`-CanPassthrough`仍保留原有MAVLink ISR发送路径，本队列只覆盖普通CAN_CIA402应答。

## CANopen与平台必要适配

CANopen接收恢复原来的匹配过滤后直接分派：NMT/SYNC和本节点的低7位匹配报文进入栈，不再用新增功能码白名单拦截本节点0x700远程节点守护。远程帧匹配策略恢复母体FDCAN_FILTER_REMOTE语义。复制到CanFestival Message时仍保留8字节容量边界。

保留HPM GPTMR2通道1的微秒累计时基、重装和比较值处理，避免初版移植将长等待压成1ms或重复累计。这是硬件时基适配，不是修改CanFestival库原生问题。原SDO超时库逻辑已恢复，server-only缺陷列入后续清单。

2026-11-15对齐阶段曾恢复原计数和掉线门控；这属于历史记录。后续A05已增加HOST门控，A06已按本节点可处理的协议活动统一计数，当前合同及证明边界见文末。

## MAVLink透传对齐

原工程在CAN-host模式下不再解析UART MAVLink，本工程恢复该互斥：UART完整MAVLink帧被消费但不派发，避免与CAN共用COMM_0；UART文本console仍保留，二进制帧不会直接作为console命令输入。

默认映射sys_id=1，comp_id来自当前CAN节点的低8位，避免应用层固定15与BSP过滤节点分裂。过滤器仍在初始化生成，改节点后的扩展过滤生效时机与母体一致，需重启。原节点大于255时的8位映射限制不在本阶段优化。BRS约定、分包和原有并发限制仍需按目标使用场景验收。

## 配置与诊断

波特率配置下次初始化/重启生效。CANopen节点与过滤器也在初始化时一起生效；普通CAN按当前节点逐帧比较。保留`can`状态与`can diag`只读寄存器快照，显示配置/生效节点、波特率、收发/溢出/BO计数及首次BO快照。`can`在原有输出后新增`reply`/`split`/`legacy`和`replyq pending/drop/highwater`，旧字段和原输出行保持不变；启动信息也显示应答ID及split/legacy模式。PSR读取会消耗LEC/DLEC状态，不把读诊断等同清故障。

前面新增的`can reset`、主循环bus-off扩展反应已撤回，运行恢复按原重启初始化流程。`can`的ready表示初始化成功，不代表已经排除总线错误，应结合diag观察。没有新增自动恢复或使能行为。

## A02错误返回契约（2026-11-17）

普通CAN新默认与LegacySameId均使用同一错误帧格式，仅CAN ID规则不同。成功帧仍op=0/1；错误帧op=0x80，索引/子索引不变，后4字节为32位小端abort。旧客户端必须识别0x80，不能只等待原op回显。LegacySameId只兼容ID规则，不保留旧“失败仍正常回显”。

|错误|错误码|
|---|---|
|写只读对象|0x06010002|
|对象不存在|0x06020000|
|已有子索引校验拒绝|0x06090011|
|APP参数越界|0x06090030|
|权限或状态不允许|0x08000022|
|未知APP返回错误|0x08000000|

例如BUS权限下写605A=8失败，节点21回复`0x415 [80 5A 60 00 30 00 09 06]`；合法写605A=3仍回复`[01 5A 60 00 03 00 00 00]`。HOST拒写为`0x08000022`。错误是请求结果，不会因此自动设置驱动故障。

44个含APP调用的OD setter（51调用点）检查返回值，失败恢复对应OD缓存；单位换算、getter、纯OD setter及控制字同步机制未改。没有增加或删除对象，CSV/EDS/对象布局未变；自动再生成保持性仍为C06待验。未知模式的接受/APP内部部分写入属于A03，标量子索引不足仍属于A04；EtherCAT回调旧返回行为也未在A02处理，不能将此合同泛化到未校验的输入或其它协议。

此错误帧用于已受理且OD回调返回错误的请求。非法帧或队满未受理仍按各自策略忽略/计数，队满无空位时不保证额外abort回复，也不执行该写操作。FIFO暂满按A01保留重试。

实机：普通CAN与CANopen SDO均验证只读、未知对象、越界、已有数组子索引错误及HOST拒写，100轮错误后有效读取可恢复；调试器在getter刷新之前确认失败后的Quickstop OD缓存仍2，合法2→3→2通过。Legacy单在途错误测试通过，Legacy突发仍有A01已声明的同ID竞争限制。A01的5000读、3x20/3x128/512请求列、节点边界、30轮失能转换和五配置/CUSTOM125回归通过。详见工程外native-fixes-20261117/a02/RESULT.md。

## A06 有效入站活动计数（2026-11-17）

`can` 的 `rx`、`servo_can_status_t.rx_count` 与 `bsp_get_can_mg_counts()` 使用同一个有效入站活动计数；它不是物理总线原始帧数，也不代表对象写入或应答发送成功。0 表示初始化后从未收到符合当前协议保活条件的活动；32位计数回绕时跳过0。
